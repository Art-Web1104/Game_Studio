# R2 유닛 1: 룰렛 생산용 CSPRNG 추첨 경계

- 작업: `R2-RNG-0001`
- 계약: `games/roulette/rng-contract.yaml` (`RNG-ROULETTE-R1`)
- 구현: `studio_core/rng.py`
- 독립 통계: `studio_core/rng_stats.py`
- 기록 스키마: `games/roulette/rng-draw-record.schema.json`
- 검증: `scripts/validate_baseline.py::validate_r2_rng`, `tests/test_rng.py`

## 1. 이 유닛이 닫는 위험

`docs/approvals/R1-validation-report.md`가 R2로 이월한 기술 위험 세 가지 중 첫 번째,
"생산용 CSPRNG 구현과 독립 통계 검증"을 닫는다. 나머지 두 가지(데이터베이스 격리·동시성·장애
복구, 실제 네트워크 재접속·부하·보안 침투 시험)는 이 유닛의 범위가 아니며 후속 R2 유닛으로
그대로 남는다.

## 2. 경계 설계

추첨 경계는 하나의 책임만 갖는다. 인가된 추첨 요청을 `0..36` 포켓 하나와 감사 가능한 기록으로
바꾸는 것이다.

```
DrawRequest ─▶ RouletteDrawEngine ─▶ draw_pocket ─▶ EntropySource
                     │                                (OS CSPRNG)
                     ├─▶ AuditSink (감사 선기록)
                     └─▶ DrawRecord ─▶ 정산·라운드 문서
```

`studio_core/rng.py`는 `studio_core/roulette.py`와 `studio_core/ledger.py`를 임포트하지 않는다.
의존 방향이 한쪽으로만 흐르기 때문에 "RNG는 지급 테이블의 영향을 받을 수 없다"가 리뷰 약속이
아니라 구조적 성질이 된다. 정산은 기록된 `pocket`만 읽고 엔트로피 경로에 접근하지 않는다.

## 3. 편향 없는 매핑

바이트는 256개 값을 갖고 휠은 37개 포켓을 갖는다. `byte % 37`은 34개 포켓이 7번, 3개 포켓이
6번 나오는 편향된 매핑이다. 따라서 `ACCEPTED_BYTE_LIMIT = 222 = 37 × 6` 이상인 바이트를 모두
거부하고 남은 222개 값만 `% 37`로 매핑한다. 각 포켓이 정확히 6개의 채택 값을 갖는다.

이 성질은 표본추출이 아니라 열거로 증명한다. `mapping_distribution()`이 0..255 도메인을 전수
순회하고, 검증기와 테스트가 "37개 포켓 각 6개, 거부 34개, 합계 256"을 확인한다. 표본은 편향을
반증할 수는 있어도 부재를 증명할 수 없으므로, 증명은 열거가 맡고 표본은 다른 일을 맡는다.

거부는 절대 편향된 대체 매핑으로 되돌아가지 않는다. `MAX_REJECTION_ATTEMPTS = 128`을 소진하면
라운드를 무효화한다. 거부 확률이 `34/256`이므로 128회 연속 거부는 약 `1e-115` 사건이고, 이는
재시도할 상황이 아니라 엔트로피원이 고장 난 상황이다.

## 4. 생산 엔트로피원

`OsCsprngEntropySource`가 유일한 생산 엔트로피원이다. `secrets.token_bytes`는 `os.urandom`에
위임하고, 이는 플랫폼 CSPRNG(`getrandom(2)` / `BCryptGenRandom`)이다. 애플리케이션이 보유한
시드가 없으므로 저장하거나 유출할 시드도 없다.

`DeterministicTestEntropySource`는 테스트와 인증용 재현 가능 스트림이다.
`RngEnvironment.PRODUCTION`과 결합되면 엔진 생성 자체가 `DETERMINISTIC_SOURCE_IN_PRODUCTION`
(`BLOCK_AND_ESCALATE`)으로 거부되므로, 실수로 주입되어도 생산 추첨에 도달할 수 없다.

## 5. 비밀 위생

원시 엔트로피 바이트, 시드 값, 거부 횟수는 기록·감사 이벤트·예외 메시지·어댑터 `repr`
어디에도 남지 않는다. 거부 횟수를 의도적으로 제외한 이유는, 거부 1회가 "뽑힌 바이트 하나가
`222..255` 구간이었다"는 CSPRNG 출력 스트림에 대한 실제 정보이기 때문이다.

`seed_reference`는 시드 값이 아니라 엔트로피 권위의 참조다. OS CSPRNG에는 애플리케이션이 볼 수
있는 시드가 없으므로 참조할 시드 값 자체가 존재하지 않는다.

금지 필드는 `PROHIBITED_RECORD_FIELDS`로 열거되고, 기록 스키마의 `additionalProperties: false`가
구조적으로 거부하며, 검증기와 테스트가 그 두 층을 모두 확인한다.

## 6. 실패 폐쇄와 감사 선기록

모든 게이트는 `games/roulette/rng-contract.yaml`이 선언한 실패 동작을 담은 `RngDenied`를 던진다.

| 상황 | 코드 | 동작 |
| --- | --- | --- |
| 결정론 어댑터 + 생산 환경 | `DETERMINISTIC_SOURCE_IN_PRODUCTION` | `BLOCK_AND_ESCALATE` |
| 알고리즘·버전 불일치 | `ALGORITHM_VERSION_MISMATCH` | `BLOCK_AND_ESCALATE` |
| 동일 `request_id`, 다른 파라미터 | `DUPLICATE_REQUEST_CONFLICT` | `BLOCK_AND_ESCALATE` |
| 이미 추첨된 라운드 | `ROUND_ALREADY_DRAWN` | `BLOCK_AND_ESCALATE` |
| 엔트로피원 실패·단축 읽기 | `ENTROPY_SOURCE_FAILED` / `ENTROPY_SOURCE_INVALID` | `VOID_ROUND` |
| 거부 128회 소진 | `ENTROPY_REJECTION_EXHAUSTED` | `VOID_ROUND` |
| 감사 기록 실패 | `AUDIT_WRITE_FAILURE` | `BLOCK_AND_VOID` |

추첨 결과는 감사 이벤트가 수락된 뒤에만 성립한다. 감사 싱크가 실패하면 이미 뽑힌 포켓을
폐기하고 라운드를 무효화하므로, 감사 불가능한 결과가 정산될 수 없다.

`VOID_ROUND`와 `BLOCK_AND_VOID` 실패는 각 `raise` 지점이 아니라 `draw()` 경계에서 일괄
처리되어 라운드를 무효 집합에 넣는다. 시계 오류나 엔트로피 고갈이 발생한 시점에는 이미 포켓이
뽑혀 폐기된 뒤일 수 있고, 라운드를 그대로 두면 오류를 유발할 수 있는 운영자가 같은 라운드를
다시 굴릴 수 있기 때문이다. 이 재추첨은 감사 기록에도 남지 않으므로 무효화가 유일한 차단선이다.

거부된 추첨도 `SECURITY` / `DENY` 감사 이벤트로 남는다. 성공만 기록하면 "표본 추출 → 폐기 →
재추출" 순열이 감사자에게 완전히 보이지 않게 되는데, 그것이야말로 감사 기록이 드러내야 할
패턴이다. 감사 싱크가 죽어 있으면 거부 기록은 조용히 생략된다. 이미 실패 폐쇄 중인 호출을
로깅 장애로 두 번 실패시키면 원래 오류가 가려지기 때문이다.

`void_round()`는 정산을 영구히 막는 권위 상태 변경이므로 `round_id`와 사유를 검증하고
`ROULETTE_RNG_ROUND_VOIDED` 이벤트를 남긴다.

동일 `request_id` 재요청은 원본 기록을 그대로 반환한다(`RETURN_ORIGINAL_RESULT`). 라운드당 권위
추첨은 하나이며, `request_id`가 멱등 경계다. 이 검사와 기록 저장 사이에는 엔트로피 읽기와 감사
기록이 끼어 있으므로 `draw()` 전체를 락으로 직렬화한다. 락이 없으면 같은 `round_id`로 경쟁하는
두 호출이 모두 "주인 없음"을 관측하고 각자 추첨해, 이 유닛이 지키려는 불변식이 게임 서버에
실제로 존재하는 동시성 아래에서 깨진다.

## 6-1. 증명 재검증

`verify_draw_record()`가 저장된 기록에서 `proof_hash`를 다시 계산해 불일치 시
`PROOF_INVALID`(`VOID_ROUND`)를, 증명 재료가 없으면 `PROOF_MISSING`을 던진다. 추첨 시점에
증명을 계산하는 것만으로는 계약의 `missing_or_invalid_proof: VOID_ROUND`를 만족할 수 없다.
나중에 그것을 **검사**할 수 있어야 저장소에서 편집된 기록과 진짜 기록이 구별된다. 정산은 엔진에서
직접 받지 않은 기록에 대해 지급 전 이 검사를 수행해야 한다.

## 6-2. 계약과의 알려진 편차

`games/roulette/rng-contract.yaml`의 `interface.input`은 `protected_seed_reference`를 추첨
입력으로 선언하지만, `DrawRequest`에는 이 필드가 없다. 엔진이 자신의 엔트로피원에서 직접
`seed_reference`를 유도하기 때문이다. 이는 호출자가 시드 참조를 지정할 수 없다는 뜻이며 서버
권위 관점에서 더 강한 선택이다. 검증기는 선언된 `interface.output` 3종이 실제 추첨 기록에
존재하는지 확인하고 이 편차를 명시적으로 기록한다. 계약 문구 개정은 `A-02`·`A-20` 검토
사항으로 남긴다. R1 승인 산출물을 이 작업에서 일방적으로 수정하지 않았다.

## 7. 증명 해시의 범위

`proof_hash`는 추첨 요청과 결과 사이의 변조 탐지 바인딩이다. 기록만 가진 감사자가 재계산할 수
있고 엔트로피를 포함하지 않는다. 이것은 기록이 사후 편집되지 않았음을 증명하지만, 커밋-공개
방식의 사용자 검증 가능 공정성 증명은 **아니다**. 공정성 증명 도입 여부는
`tasks/R2-RNG-0001.json`의 `open_decisions`에 미결로 남아 있다.

## 8. 독립 통계 검증

`studio_core/rng_stats.py`는 `studio_core/rng.py`를 임포트하지 않는다. 정수 수열과 포켓 수만
입력으로 받는다. 생성기와 코드를 공유하는 통계 모듈은 생성기의 실수를 그대로 물려받아 그것을
인증할 수 있기 때문에, 이 독립성이 모듈의 존재 이유다.

| 검정 | 자유도 | 무엇을 잡는가 |
| --- | --- | --- |
| `POCKET_UNIFORMITY` | 36 | 특정 포켓이 장기적으로 우대되는 편향. 하우스 엣지를 직접 움직인다. |
| `SERIAL_INDEPENDENCE` | 1368 | 전체적으로는 균등하지만 직전 결과로 다음이 예측되는 의존성 |
| `REJECTION_RATE` | 1 | 채택률이 선언된 `222/256`에서 이탈. 디바이어싱 경로가 명세대로 돌지 않는 경우 |

인접쌍 검정은 겹치지 않는 쌍만 사용한다. 겹치는 쌍은 추첨 하나를 공유해 카이제곱이 가정하는
셀 독립성을 깨기 때문이다. 카이제곱 꼬리 확률은 정규화 상부 불완전 감마 함수로 계산하므로
외부 의존성도, 임계값 표도 필요 없다. 셀당 기대도수가 5 미만이면 모듈은 부정확한 판정을
내리는 대신 판정을 거부한다.

통과는 "결함을 탐지하지 못했다"는 뜻이지 정확성의 증명이 아니다. 균등성의 증명은 3절의 열거가
맡고, 이 검정들은 열거가 가정한 "균등한 엔트로피원"이 실제로 그렇게 동작하는지를 본다.

## 9. 범위 밖과 이월 위험

- 데이터베이스 격리 수준, 동시성 제어, 장애 복구 (후속 R2 유닛)
- 실제 네트워크 재접속, 부하 시험, 보안 침투 시험 (후속 R2 유닛)
- **엔진 상태의 비내구성.** 기록·라운드 소유권·무효 집합은 인메모리다. 락은 한 프로세스 안의
  스레드 경쟁만 막는다. 프로세스가 재시작되면 모든 `request_id`를 잊으므로, 재시작 이후의
  클라이언트 재시도는 같은 라운드에 두 번째 권위 결과를 만들 수 있다. 내구 저장소가 생기기
  전까지 이 엔진을 멱등성의 기록 원본으로 취급해서는 안 된다.
- **`audit_event_ref`의 전역 유일성 부재.** 명시적 싱크 없이 만든 엔진은 각자 `AuditChain("RNG")`
  를 갖고 순번이 1부터 다시 시작하므로, 두 테이블이 모두 `audit://AE-RNG-0001`을 발행할 수 있다.
  내구 감사 저장소 유닛에서 네임스페이스에 테이블·인스턴스 식별자를 포함해야 한다.
- **감사 체인의 9999 이벤트 한계.** 초과 시 `AUDIT_SEQUENCE_EXHAUSTED`(`BLOCK_AND_VOID`)로 실패
  폐쇄되지만 세그먼트 분할 로직이 없어 분당 1회 추첨 기준 약 7일 뒤 테이블이 멈춘다. 세그먼트
  롤오버는 내구 감사 저장소 유닛의 범위다.
- 감사 체인의 내구성 저장소. 현재 `AuditChain`은 이벤트 형태와 연결 규칙을 고정하는 인메모리
  참조 구현이며, 내구 구현이 맞춰야 할 실행 가능한 목표다.
- 커밋-공개 공정성 증명
- R5 이전이므로 상용 제작 일정과 출시일은 확정하지 않는다.

## 10. 통계 증거를 읽는 법

두 곳에서 통계가 돌고, 둘은 서로 다른 것을 증명한다.

| 위치 | 엔트로피원 | 성격 |
| --- | --- | --- |
| `scripts/validate_baseline.py::validate_r2_rng` | 고정 시드 Mersenne Twister | 결정론적 회귀 검사. 모든 기계에서 같은 판정이 나와야 하므로 CSPRNG가 아니다. **생산 엔트로피원 인증이 아니다.** |
| `tests/test_rng.py::LiveCsprngCertificationTests` | 실제 OS CSPRNG | 생산 엔트로피원의 실제 인증 |

검증기 표본을 60000회로 잡은 이유는 이 검정이 막아야 할 구체적 결함, 즉 순진한 `byte % 37`
(34개 포켓 7/256, 3개 포켓 6/256)에 대한 검정력이다. 20000회에서는 비중심 모수가 약 31이라
0.001 임계값 67.985에 대해 검출 확률이 사실상 동전 던지기다(실측 21/40). 60000회에서는 비중심
모수가 약 93으로 올라가 실측 40/40으로 검출된다. 그럼에도 무편향성의 **증명**은 3절의 열거이며,
통계는 그 증명이 가정한 엔트로피원의 실제 거동을 볼 뿐이다.
