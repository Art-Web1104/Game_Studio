# R4 유닛 1: 내부용 로컬 플레이어블 룰렛 수직 슬라이스

- 작업: `R4-UI-0006`
- 위험 등급: `HIGH`
- 상태: 구현 완료, **인간 게이트 미발행**
- 산출물: `apps/roulette_web/`, `games/roulette/playable-slice-contract.yaml`,
  `tests/test_roulette_web_server.py`, `tests/test_roulette_web_ui.py`,
  `scripts/validate_baseline.py::validate_r4_playable_slice`
- 실행: `python -m apps.roulette_web.server` (자세한 실행·중지·조작은
  `apps/roulette_web/README.md`)

**내부 프로토타입입니다. 가상 칩만 사용하며 현금 가치가 없습니다.**

이 문서는 설계 기록이다. 게이트 판정도, 착수 허가도, 배포 승인도 아니다. 일정, 기간, 마감,
출시일을 정하지 않으며 `R5` 승인 전에는 상용 제작 일정을 확정하지 않는다.

## 1. 이 유닛이 닫는 것과 닫지 않는 것

닫는 것: `R1`과 `R2`에서 계약과 코어 경계로만 존재하던 유러피언 싱글제로 룰렛을 사람이 실제로
조작해 볼 수 있는 하나의 수직 슬라이스로 잇는다. 베팅 입력부터 추첨, 정산, 잔액 갱신, 최근 결과
표시까지가 하나의 권위 경로를 통과한다.

닫지 않는 것: 네트워크 재접속 보증(`R2-NET-0003`), 부하·성능 특성(`R2-LOAD-0004`), 침투
시험(`R2-SEC-0005`), 다중 사용자 동시 테이블, 세션 분리, 운영 배포, 수익화, 상용 클라이언트
결정. 이 문서와 코드의 어떤 부분도 그것들을 구현했다고 주장하지 않는다.

## 2. 층 구조

```
브라우저 (HTML · CSS · JavaScript, 빌드 단계 없음)
        │  fetch /api/state · /api/bets · /api/spin · /api/new-round
        ▼
apps/roulette_web/server.py      전송 계층. 파싱·거부·정적 배급만 한다.
        ▼
apps/roulette_web/table.py       권위 계층. 라운드 상태·검증·정산·스냅샷.
        ▼
studio_core.roulette             규칙과 정산 (R1 승인 기준선)
studio_core.rng                  추첨 경계 (R2-RNG-0001 승인 기준선)
studio_core.durable_state        단일 트랜잭션 커밋 (R2-DBC-0002 승인 기준선)
```

`studio_core`의 네 모듈(`rng`, `roulette`, `durable_state`, `ledger`)은 **수정하지 않았다.**
공개 인터페이스로만 사용하며, 이 유닛은 규칙·엔트로피·원장·내구성의 두 번째 구현을 만들지
않는다. `tasks/R4-UI-0006.json`이 네 모듈의 해시를 입력으로 선언하므로 무결성 검증이 이
사실을 매 실행마다 확인한다.

## 3. 권위 경계

플레이어가 잘못 말해서 이득을 볼 수 있는 값은 전부 서버에서만 생성된다: 결과 포켓, 승패,
지급액, 잔액, 최근 결과 목록.

- 클라이언트는 **의도만** 보낸다(`이 베팅을 담아라`, `돌려라`, `새 라운드`).
- 결과·지급액·잔액 필드를 실은 요청은 조용히 무시하지 않고 `CLIENT_AUTHORITY_DENIED`로
  **거부한다.** 조용히 버려진 필드는 다음 리팩터링이 되살릴 수 있는 필드다.
- 클라이언트에는 난수원이 없다. 휠은 서버가 정한 숫자 주위를 도는 장식이며, 결과 쪽으로
  회전할 뿐 결과를 만들지 않는다.
- 포켓 색(빨강·검정·초록)조차 서버가 붙여 보낸다. 클라이언트가 `32는 빨강`을 재계산하면
  버전이 없는 규칙 사본이 하나 더 생기고, 불일치를 가장 먼저 발견하는 사람은 플레이어가 된다.
- 보드의 번호 칸과 선택 개수는 `/api/state`가 보낸 목록으로 만든다. 권위 테이블이 모르는
  베팅을 화면이 먼저 제안할 수 없다.

## 4. 라운드 상태

`games/roulette/round-state.yaml`이 원본이고, `apps/roulette_web/table.py`의 `TRANSITIONS`는
그 표를 데이터로 옮겨 적은 것이다. 검증기가 두 표를 항목별로 대조하므로 한쪽만 바뀌면 기준선이
실패한다.

```
OPEN ──▶ LOCKED ──▶ SPINNING ──▶ SETTLING ──▶ SETTLED
  │         │           │
  └─────────┴───────────┴────▶ VOIDED
```

- 베팅은 `OPEN`에서만 받는다.
- 추첨은 `SPINNING`에서만 일어난다.
- 원장 정산 본문은 `SETTLING`에서만 만들어진다. 그 전이는 정산 팩토리가 실제로 호출되는
  순간에 일어나므로, 재생된 제출은 그 지점에 도달하지 않는다.
- 종결 상태(`SETTLED`, `VOIDED`)는 변경할 수 없다.
- 커밋이 이루어지지 않은 라운드는 결과를 받지 못하고 `VOIDED`로 닫힌다. 원래의 거부 사유는
  가려지지 않고 그대로 호출자에게 전달된다.

## 5. 정수 가상 칩과 원장

통화 값은 어디서나 정수 최소 단위다. 요청 본문의 소수점 숫자는 JSON 파서 단계에서 거부된다
(`parse_float`가 실패로 닫는다). 잔액, 베팅액, 지급액, 증감이 모두 `int`이며 부동소수 통화
값은 생성되지도 저장되지도 전송되지도 않는다.

정산은 라운드당 하나의 `ROUND_SETTLEMENT` 트랜잭션이다. `economy-model.yaml`이 요구하는
에스크로 왕복은 두 번의 커밋으로 쪼개지 않고 같은 트랜잭션의 엔트리 안에 보존된다: 베팅액이
플레이어에서 `BET_ESCROW`로 나가고, 에스크로가 비워지고, 차액이 하우스 뱅크롤과 정산된다.

베팅이 담기는 시점에는 칩이 빠져나가지 않으므로, 아직 돌리지 않은 라운드에서 보유량보다 많이
거는 일이 가능해진다. `_reserved_units`가 그것을 닫는다. 열린 베팅액은 검증 시점에 잔액에
예약되고, 정산이 초과 인출을 처음 발견하는 순간이 되지 않는다. 하우스 쪽은 기댓값이 아니라
**37개 포켓 전체를 실제로 평가한 최악의 지급액**으로 검사한다. 하우스는 평균 포켓이 아니라
실제로 떨어진 포켓을 지급해야 하고, 37개는 정확히 계산할 만큼 작은 공간이다.

## 6. 멱등성

`request_id`가 API 전체의 멱등성 경계다.

- 같은 식별자로 같은 내용을 다시 보내면 엔트로피를 다시 소비하지 않고 원본 결과를 그대로
  돌려준다. 스핀의 경우 `request_id`가 `DrawRequest.request_id`로 그대로 들어가므로 내구
  저장소의 재생 경로가 이를 보장하고, 재시작 이후에도 유지된다.
- 같은 식별자를 **다른 내용으로** 재사용하면 `REQUEST_ID_CONFLICT`로 실패로 닫힌다. 관련 없는
  이전 응답을 돌려주는 것은 새 요청이 성공했다고 거짓말하는 일이다.
- 클라이언트의 요청 식별자는 난수가 아니라 적재 단위 토큰 위의 단조 증가 계수기다. 재시도는
  **재시도하는 시도의 식별자를 다시 써야** 하며, 그렇지 않으면 응답이 유실된 스핀이 두 번
  청구된다. 화면의 `다시 시도` 버튼이 정확히 그 동작을 한다.

## 7. 재시작이 지키는 것

커밋된 것만 지킨다. 잔액, 추첨 기록, 정산, 감사 체인은 전부 데이터베이스에서 다시 읽으므로
재시작 뒤의 최근 결과 목록은 **저장된 커밋 순서**이지 클라이언트가 준 이력이 아니다. 최근 결과는
감사 체인을 따라 만들어진다. `event_seq`가 기록과 같은 트랜잭션 안에서 부여되므로 체인이 곧
커밋 순서이기 때문이다.

열린 라운드의 베팅은 의도적으로 내구적이지 않다. 커밋된 것이 없고 엔트로피도 쓰지 않았으며,
반쯤 만들어진 베팅 보드를 복원하려면 승인된 스키마에 없는 내구 표현을 발명해야 한다. 재시작은
새 라운드를 열고, 플레이어는 제출하지 않은 선택 외에 잃는 것이 없다.

## 8. 전송 계층의 거부 규칙

전송 계층은 규칙을 하나도 알지 못하고, 열기보다 닫는 쪽으로 실패한다.

| 대상 | 규칙 |
| --- | --- |
| 바인딩 | 루프백만. 루프백 밖으로 풀리는 호스트는 바인딩 전에 거부. 기본값은 `127.0.0.1`. |
| 크기 | `Content-Length` 필수, 8 KiB 상한, 본문을 **읽기 전에** 검사. 청크 전송 거부. |
| 모양 | 본문은 JSON 객체여야 한다. 권위 필드를 담으면 정화하지 않고 거부. |
| 메서드 | 경로마다 선언된 한 가지 메서드만. `PUT`·`DELETE`·`PATCH`·`OPTIONS` 거부. |
| 오류 | 항상 안정된 코드가 있는 JSON 객체. 스택 추적·파일 경로·데이터베이스 메시지 비노출. |
| 정적 자산 | 한 디렉터리에서만, `resolve()` 후 포함 관계 확인, 확장자 허용 목록과 고정 타입. |

경로 탐색 방어는 `..` 문자열 검사가 아니라 **정규화 후 포함 관계 확인**이다. 차단 목록은 모든
표기를 예상해야 하지만 `resolve()`는 그것들을 전부 접고, `is_relative_to`가 유일하게 중요한
질문에 답한다 — 호출자가 지목한 파일이 실제로 우리가 배급하는 디렉터리 안에 있는가. 트리 밖을
가리키는 심볼릭 링크도 같은 검사로 걸린다.

`BaseHTTPRequestHandler`의 기본 오류 페이지는 서버 이름과 실패한 요청 줄이 적힌 HTML이다.
`send_error`를 재정의해 이 프로세스의 모든 응답을 내부 정보가 없는 하나의 JSON 모양으로
통일했다.

## 9. 보안 헤더와 클라이언트 자산

모든 응답에 `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`,
`Referrer-Policy`, `Cross-Origin-Resource-Policy`, `Permissions-Policy`, `Cache-Control`이
붙는다. CSP는 `default-src 'none'`에서 시작해 `script-src 'self'`, `style-src 'self'`만
허용하며 `'unsafe-inline'`이 없다. 그래서 마크업에는 인라인 `<script>`, 인라인 `<style>`,
`style="…"` 속성이 하나도 없다. 있으면 브라우저가 거부한다.

모든 자산은 이 루프백 출처가 배급한다. 글꼴·스크립트·스타일·이미지 중 외부에서 오는 것이
없고, 그래서 예외 없는 정책을 보낼 수 있다. Node.js와 npm이 없는 환경을 가정하므로 번들러도
프레임워크도 CDN도 쓰지 않는다.

## 10. 접근성과 반응형

모바일 세로 화면을 기준으로 설계하고 선언된 중단점에서 넓힌다. 조작 요소는 전부 실제 `button`과
`input`이며 키보드만으로 전 과정을 수행할 수 있다. 보이는 포커스 표시가 항상 있고,
`prefers-reduced-motion`을 존중해 휠 회전 연출을 끄며, 라운드 상태·결과·잔액 변화는
`aria-live` 영역으로, 오류는 `role="alert"`로 안내된다. 건너뛰기 링크와 `noscript` 대체가
있다.

**이 검증은 정적이다.** 마크업 구조, 스타일시트 규칙, 접근 가능한 이름의 존재를 시험으로
확인했을 뿐이며, 실기기 브라우저와 화면 낭독기를 사용한 사람 검사는 수행하지 않았다. 자동
시험은 그 검사를 대체하지 않는다.

## 11. 공개 문구

모든 화면과 모든 API 응답이 내부 프로토타입·가상 칩·현금 가치 없음을 한국어와 영어로 싣는다.
구매·충전·환전·결제·실물 보상·수익화·출시 일정을 시사하는 문구나 경로는 존재하지 않으며,
시험이 클라이언트 자산 전체와 서버 응답을 대상으로 금지 용어와 금지 경로를 스캔한다.

## 12. 런타임 상태의 위치

권위 상태는 SQLite 파일 하나이고 **저장소 밖**에 만들어진다. 기본값은 플랫폼 임시 디렉터리
아래이며 `--db` 또는 `ROULETTE_WEB_DB`로 옮길 수 있다. 작업 트리 안을 가리켜 실행하더라도
`.gitignore`가 데이터베이스와 WAL/SHM 사이드카를 제외한다. 프로토타입의 잔액은 저장소 내용이
아니다.

## 13. 실패 동작 표

| 상황 | 동작 | 코드 |
| --- | --- | --- |
| 규칙에 없는 베팅 유형·선택 집합 | 거부, 상태·잔액 불변 | `BET_INVALID` |
| 예약 후 잔액 초과 | 거부, 상태·잔액 불변 | `INSUFFICIENT_CHIPS` |
| 하우스 최대 책임 초과 | 거부, 상태·잔액 불변 | `HOUSE_EXPOSURE_EXCEEDED` |
| `OPEN`이 아닌 상태의 베팅·스핀 | 거부 | `PHASE_DENIED` |
| 종결 라운드 변경 시도 | 거부 | `TERMINAL_STATE` |
| 선언되지 않은 전이 | 거부 | `TRANSITION_DENIED` |
| 같은 식별자·다른 내용 | 실패로 닫힘 | `REQUEST_ID_CONFLICT` |
| 이전 프로세스가 이미 쓴 식별자 | 라운드 무효화 후 거부 | `REQUEST_ID_ALREADY_USED` |
| 추첨 경계 거부 | 라운드 무효화, 코드만 전달 | `DRAW_DENIED` |
| 커밋 경계 거부 | 라운드 무효화, 코드만 전달 | `COMMIT_DENIED` |
| 권위 필드를 실은 요청 | 거부 | `CLIENT_AUTHORITY_DENIED` |
| 소수점 통화 값 | 파서 단계 거부 | `BAD_JSON` |
| 8 KiB 초과 본문 | 본문을 읽지 않고 거부 | `PAYLOAD_TOO_LARGE` |
| 길이 미선언·청크 전송 | 거부 | `LENGTH_REQUIRED` |
| 알 수 없는 경로·경로 탐색 | 거부, 내부 정보 비노출 | `NOT_FOUND` |
| 허용되지 않은 메서드 | 거부 | `METHOD_NOT_ALLOWED` |
| 예상치 못한 내부 예외 | 평면 오류, 내부 정보 비노출 | `INTERNAL_ERROR` |

## 14. 계약과 검증기

`games/roulette/playable-slice-contract.yaml`이 엔드포인트, 요청·응답 필드, 권위 경계, 상태
전이, 오류 코드, 보안 헤더, 정적 자산 허용 목록을 선언한다.
`scripts/validate_baseline.py::validate_r4_playable_slice`가 그 선언을 구현 상수와 항목별로
대조하고, 클라이언트 자산에 난수원·지급 표·잔액 산술이 없음을 확인하며, 아티팩트의 구성요소
해시가 현재 파일과 일치하는지, 인간 승인 항목이 체크되지 않은 채로 남아 있는지,
`R2-NET-0003`·`R2-LOAD-0004`·`R2-SEC-0005`가 여전히 이월 상태로 기록되어 있는지 확인한다.
